# Windows Steam build 40425: the update of 2026-10-24

Transport Fever 3 updated on Steam from build 40423 (Steam build ID
25962684) to 40425 (26129055) on 2026-10-24. The 1.3.3 hook, built for
40423, refuses it: no compiled native bundle matches the new executable, so
multiplayer stays off (fail-closed). This note is the evidence for the new
bundle `profiles/tf3_build40425_steam_windows/`, now selected in
`profiles/native-build.txt`. It is static: the real-game acceptance
(GAME_TESTING.md) is listed as open at the end.

| identity | 40423 | 40425 |
|---|---|---|
| Steam build ID | 25962684 | 26129055 |
| SHA-256 | `e6c67da0…a658177e` | `e9a6190f9ca8f7f34a46dfafac0f3b897e41ea6dc6498d6f5871aed6b9ca74cd` |
| executable size | 69,876,664 | 69,876,664 |
| PE timestamp | `0x6AD0E4E5` | `0x6AD9CE10` |

The executable's own build string (`transportfever3`, `64-bit`, then the
build) reads `40425`.

## Inputs and reproduction

A complete private `tpfre archive` of the installed game (7,203 files from
2,588 sources), outside Git, next to the 40423 archive. From the repository
root:

```powershell
$b = "$env:USERPROFILE/TPF3-MP-builds"
& ./tools/tpfre/target/release/tpfre.exe archive --game 'D:/SteamLibrary/steamapps/common/Transport Fever 3' --build 26129055 --steam-manifest 'D:/SteamLibrary/steamapps/appmanifest_3493540.acf' --out "$b/26129055-sources"
& ./tools/tpfre/target/release/tpfre.exe update --repo . --old "$b/25962684-sources" --new "$b/26129055-sources" --out "$b/runs/<new run>" --cache "$b/indexes" --jobs 2 --check-only
& ./tools/tpfre/target/release/tpfre.exe verify-build --repo . --archive "$b/26129055-sources" --json
```

Before the new bundle the run stopped at `signatures` and `native-bundle`
only because no bundle names the new identity: 0 changed signatures, 0
changed scripts, all 165 targets matched at their 40423 addresses, 163 of
them in functions equal with addresses masked. The other two
(`view: StationViewer::vf4/player`, `view: CSelector pick/player`) are
"unknown" because the comparer stops at a jump table in their functions
(the known limit from the 40420 update); their bytes are 40423's anyway
(below). With the bundle selected, `verify-build` exits 0
(`review_required: false`, `runtime_verified: false`).

## What changed in the game's code: only its version

The two executables were compared section by section. Every section has the
same address and size. Apart from SteamStub's `.bind` section (the DRM stub,
re-encrypted with each build), they differ in 43 bytes, all version data:

| where | 40423 | 40425 | what it is |
|---|---|---|---|
| `.text` `0x84cbb`, `0x84d64` (the immediates of two `mov rcx,imm64`) | `"525626a2"` | `"8830bc37"` | an 8-character source revision written into two strings |
| `.text` `0x3055b31` (the immediate of `mov eax`) | `0x9de7` | `0x9de9` | a function that returns the build number (40423 → 40425) |
| `.rdata` `0x3888590` | `40423` | `40425` | the build string |
| `.rdata` `0x38bf764`, `0x38bf780`, `0x38bf79c` | `0x6AD0E4E5` | `0x6AD9CE10` | the debug directory's timestamps |
| `.rdata` `0x39eb4fc` | | | the PDB's GUID |

`.text` differs in 17 bytes in all, none inside a function the profile
names or a byte the bundle reads. So every target keeps its address,
signature and prologue, and every native constant of the 40423 bundle
(vtables, pool vtables, simulation timer slots, emission hashes, splice
bytes, field offsets, the command layout) holds unchanged: the bundle is
40423's with its identity changed (`hooks.toml`'s `[build]` and name,
`industry_probe.toml`'s, `native.rs`' Steam and game build), and each
file's comment names 40425.

## Code outside the bundle

- `crates/tpf3mp-hookcore/tests/tf3_build40425_profile.rs`: the 40423
  static proof with the identity changed; every fact it asserts is re-read
  from the 40425 executable when `TPF3MP_TF3_BUILD40425_EXE` names it.
- `interval.rs`: 40425 joins the builds with the verified step layout
  (`CGame::Step`, `CGame::Sync` and `RunGameSimLoop` are 40423's bytes at
  40423's addresses). 40424 and 40426 still get none.
- `menu_entry.rs`: the line manager window copy is served on 40425 too. The
  game's `gui/line_vehicle_mgmt/manager_window.tl` (SHA-256 `9608c068…`) and
  `gui/menu/main_page.tl` (`56191b18…`) are byte-identical in both builds.
- `lib.rs`: the identity test knows 40425; the compiled bundle refuses
  40408, 40420 and 40423.
- Release: `tools/github/select-game-archive.ps1` maps the 40425 bundle to
  the new repository variable `TPF3MP_GAME_ARCHIVE_40425` (DEVELOPMENT.md);
  the older archives stay verifiable.
- `tools/game/room.ps1` defaults to `-GameBuild 40425`.
- Version 1.3.4: 1.3.3 is published.

## Big Maps' plugin

The package is pinned to one executable, so the 40423 package is refused on
40425, as it must be. `src/build40425.rs` replaces `build40423.rs` with
only `BUILD` changed: all its sites, expected bytes and `CREATE_GRID_BODY`
are 40423's at the same addresses. `tests/game_40425.rs` runs the package
against the 40425 executable and the 40425 profile. A 40425 package must be
published (and the reviewed registry in `deploy/native-mods.txt` pointed at
it) for players who use Big Maps.

## Scripts and files

No script changed, was added or was removed in the game's own files.
`TransportFever3.exe`, `OpenAL32.dll`, `SDL2.dll` and `alut.dll` changed;
the three DLLs keep their size and version (OpenAL 1.22.2, SDL 2.32.8) and
differ only in their PE header's timestamp and checksum, their debug
directory and their Authenticode signature. The archive's other new files
(`mods/shinkansen_500/`, dated 2026-10-23) are a mod in the game folder,
not part of this update.

## Real-game run

- [x] Local rig, 2026-10-24, `update40425-a1`: two 40425 games attached
      with the 40425 profile (165 targets, 1 matching), the batch interval
      on, the menu reading `m_game` at `+0x8d8` and `m_loadGameResult` at
      `+0x1df8`. The host loaded `MP_Test_2` (a save made on 40420) through
      its console, the room saved it and both games played it from step 1.
      By hand: three road pieces as one chain and a bus stop on them (p1),
      two track pieces and their bulldozing (p2), a loan, then the game
      ran on to step 2800. Both games applied every room action (11 batches each);
      no refusal, no `not applied`, no divergence. The rolling world
      check's signatures (48 windows, to step 2800), the free-id hashes
      (49) and the reseeds (4) are equal in both games.
- The game reported one caught Lua error in each game, `Missing builtin
  recipeId for` `WithComponentParams` (`gui/main/react.lua:433`, reached
  through the mod's `follow.lua` under `pcall`). It is not a crash (no
  minidump) and is not new: the same report is in the game's error reports
  from earlier builds.
